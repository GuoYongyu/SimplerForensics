01 / QUICK LOOK

按你要找的信息选择入口

查看配置
01

Windows 版本与基础规格

打开“设置 → 系统 → 关于”，查看版本、版本号、处理器、已安装 RAM、系统类型和设备名称。也可按 Win + R 输入 winver 查看版本对话框。

适合：快速确认系统版本、位数和内存
02

完整系统摘要

按 Win + R 输入 msinfo32 打开“系统信息”。其中有系统摘要、硬件资源、组件和软件环境；可用“文件 → 导出”保存报告。

适合：驱动、BIOS、设备和软件环境排查
03

显卡、声音与 DirectX

运行 dxdiag 打开 DirectX 诊断工具。查看“系统”“显示”“声音”选项卡；需要提交诊断信息时，可用“保存所有信息”生成文本文件。

适合：游戏、图形和音频兼容性问题
04

逐个查看硬件设备

开始菜单搜索“设备管理器”，按类别展开处理器、显示适配器、磁盘驱动器、网络适配器等。黄色感叹号通常表示设备或驱动需要关注。

适合：识别设备型号、检查驱动状态
05

磁盘与卷

开始菜单右键 →“磁盘管理”，查看实体磁盘、分区、盘符和文件系统。设置中的“系统 → 存储”更适合查看空间占用。

适合：分清物理磁盘、分区和盘符
06

打开注册表查看器

按 Win + R 输入 regedit。左侧是键的层级树，右侧显示所选键下的值名称、类型和数据；先浏览，不要随意编辑或删除。

适合：定位程序或 Windows 配置项
命令行只读摘要在 PowerShell 中运行以下命令可查看常见硬件信息；它们只查询并输出结果。
Get-ComputerInfo | Select-Object WindowsProductName, WindowsVersion, OsBuildNumber, OsArchitecture, CsSystemType
Get-CimInstance Win32_Processor | Select-Object Name, NumberOfCores, NumberOfLogicalProcessors
Get-CimInstance Win32_PhysicalMemory | Select-Object Manufacturer, Capacity, Speed

提示：系统报告可能包含设备名、用户名、驱动、网络或硬件标识。分享之前先检查并移除不想公开的信息。

02 / USB DEVICE TRACE

USB 设备信息与连接痕迹怎么查

实用排查

先区分你要回答的问题：查“现在插着什么”应看当前设备；查“这台电脑曾安装/识别过什么”可看非当前设备、设备安装日志和注册表痕迹；查“准确的插拔时间线”则需要当时已记录相应事件。Windows 没有一个永久、完整、绝对可靠的 USB 插拔历史清单。

01

查看当前连接的 USB 设备

设备仍连接在电脑上时
  1. 右键开始菜单 →“设备管理器”。展开“磁盘驱动器”“通用串行总线控制器”“便携设备”等类别。
  2. 双击目标设备，在“常规”查看状态；“详细信息”里可选择“硬件 ID”“设备实例路径”“父级”等属性。
  3. USB 存储盘也可以打开“磁盘管理”查看磁盘和分区；谨慎区分实体磁盘、卷和盘符。
PowerShell：列出当前已枚举的 USB 设备
Get-PnpDevice -PresentOnly | Where-Object { $_.InstanceId -like 'USB\*' -or $_.InstanceId -like 'USBSTOR\*' } | Select-Object Status, Class, FriendlyName, InstanceId
Get-Disk | Where-Object BusType -eq 'USB' | Select-Object Number, FriendlyName, SerialNumber, BusType, Size, OperationalStatus

第一条针对即插即用设备实例；第二条针对 Windows 识别为 USB 总线的磁盘。个别 USB 转接盒、手机或复合设备会以其他类别/总线呈现，所以结果不一定都出现在同一条命令里。

02

查看曾经识别过的设备

设备已经拔掉时
  1. 设备管理器菜单“查看 → 显示隐藏的设备”，再查看“磁盘驱动器”“便携设备”和 USB 控制器。灰色设备通常表示当前未连接的设备节点，不代表有完整的连接时间记录。
  2. PowerShell 不加 -PresentOnly 可列出系统已登记的 PnP 设备，再按 USB 存储实例路径筛选：
Get-PnpDevice | Where-Object { $_.InstanceId -like 'USBSTOR\*' } | Select-Object Status, Class, FriendlyName, InstanceId
注册表里的常见位置
HKLM\SYSTEM\CurrentControlSet\Enum\USB

USB 设备及其枚举出来的接口/实例信息；常能看到 VID、PID、硬件 ID、设备描述等。设备管理器“详细信息”比注册表更易读。

HKLM\SYSTEM\CurrentControlSet\Enum\USBSTOR

传统 USB 大容量存储设备常见的枚举位置；路径中有时能辨认厂商、产品和实例标识。条目下可能有 DeviceDesc、Mfg、FriendlyName、HardwareID 等值，具体名称因设备而异。

HKLM\SYSTEM\MountedDevices

Windows 管理的卷标识与盘符映射信息；不是按时间排列的插拔清单。

HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\MountPoints2

当前用户相关的可移动卷挂载痕迹之一；不能单独证明具体某人在某个时间实际打开或复制过文件。

打开注册表编辑器（regedit），逐层进入路径。也可以在命令提示符查询，例如 reg query "HKLM\SYSTEM\CurrentControlSet\Enum\USBSTOR" /s。系统可能限制某些位置的读取；查询结果也可能包含设备序列号等隐私信息。查看属性时同时记下完整实例路径；若要从 VID/PID 判断厂商和型号，可将两个 ID 一起搜索核对，单看设备描述可能是通用名称。

03

查安装记录和事件时间

想定位驱动安装或事件发生时间
A · SetupAPI 设备安装日志

文件资源管理器地址栏输入 %windir%\inf\setupapi.dev.log。用记事本打开，搜索设备实例 ID 或 VID_厂商ID&PID_产品ID。它记录设备安装/配置过程，可用于核对驱动安装问题；它不是每一次插入和拔出的全量日志，旧内容也可能不再保留。

Select-String -Path "$env:windir\inf\setupapi.dev.log" -Pattern 'VID_1234&PID_5678' -Context 3,8
示例里的 VID/PID 要替换成目标设备的实际 ID。
B · 事件查看器

运行 eventvwr.msc，查看“应用程序和服务日志 → Microsoft → Windows”下的 DriverFrameworks-UserMode/Operational、DeviceSetupManager/Admin 等频道（本机名称和可用频道可能不同）。前者只涉及使用 UMDF 的设备驱动框架事件；后者常见设备设置/元数据事件。它们都不是所有 USB 插拔的统一审计频道。在频道属性中检查是否启用、日志大小/覆盖策略及最早保留时间，再按设备名、实例 ID 或时间筛选。

先列出本机名称含 USB 的事件日志及启用状态：

Get-WinEvent -ListLog '*USB*' | Select-Object LogName, IsEnabled, RecordCount

若确认 UMDF Operational 存在且有记录，可查询最近 7 天包含 USB 或 VID 字样的事件：

Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-DriverFrameworks-UserMode/Operational'; StartTime=(Get-Date).AddDays(-7)} -ErrorAction SilentlyContinue | Where-Object { $_.Message -match 'USB|VID_' } | Select-Object TimeCreated, Id, Message -First 30

查不到记录不代表设备没插过：频道可能不存在、未启用或日志已覆盖。

时间线的边界

事件频道可能不存在、未启用、被覆盖，或只记录安装/驱动事件。注册表项的“最后写入时间”也不是可靠的插拔时间。若相关日志当时没有记录，通常无法事后恢复精确的每次插拔时间。

读懂 USB 实例 IDUSB\VID_046D&PID_C534\5&2A…

VID 是厂商标识，PID 是产品标识；后续部分是实例标识，可能来自设备序列号，也可能由端口/系统生成。一个实体 USB 设备可能展开成多个设备节点，名称或节点数量不一定一一对应。

想看更完整的设备属性pnputil /enum-devices /connected

Windows 10 版本 1903 及更高版本支持该枚举参数；较新的 Windows 版本还提供更多属性筛选参数。它列出当前设备，不会自动变成历史审计报告。

03 / FILE OPERATIONS

文件拼接与拆分

命令速查

先判断文件类型。可执行文件、压缩包、图片、视频等二进制文件要按字节拼接和拆分；文本文件可以按文本行处理，但编码、换行和文件末尾换行可能被规范化。

JOIN

拼接二进制分卷

在命令提示符（CMD）中，按原始顺序列出每个分卷。/b 表示二进制模式，避免按文本方式处理文件。

copy /b "archive.part001"+"archive.part002"+"archive.part003" "archive.zip"

分卷名称要按编号顺序填写，不能漏段。CMD 显示“已复制”不代表内容一定完整；拼好后再用对应程序打开，或比对来源提供的 SHA-256。

TEXT

拼接文本文件

如果只是把多份文本内容按顺序合并，可在 PowerShell 使用：

Get-Content .\a.txt, .\b.txt | Set-Content .\merged.txt -Encoding utf8

这会按文本读取并重新写出内容，可能改变编码、换行符或末尾换行。要逐字节保持原样，请对文本也使用二进制拼接：copy /b "a.txt"+"b.txt" "merged.txt"。

SPLIT

按大小拆分任意文件

CMD 没有通用的内置二进制分块命令。下面的 PowerShell 脚本以 100 MiB 为一段读取和写出，不会把整个大文件一次性载入内存。先把 $sourcePath 改成待拆文件路径；生成文件形如 large.iso.part001、large.iso.part002。

$sourcePath = '.\large.iso'
$chunkBytes = 100MB
$buffer = New-Object byte[] (1MB)
$source = [IO.File]::OpenRead($sourcePath)
try {
    $partNumber = 1
    $remaining = $chunkBytes
    $writer = $null
    try {
        while ($true) {
            if ($remaining -eq 0) {
                $writer.Dispose()
                $writer = $null
                $partNumber++
                $remaining = $chunkBytes
            }
            $toRead = [int][Math]::Min($buffer.Length, $remaining)
            $read = $source.Read($buffer, 0, $toRead)
            if ($read -eq 0) { break }
            if ($null -eq $writer) {
                $partPath = '{0}.part{1:D3}' -f $sourcePath, $partNumber
                $writer = [IO.File]::Create($partPath)
            }
            $writer.Write($buffer, 0, $read)
            $remaining -= $read
        }
    } finally {
        if ($null -ne $writer) { $writer.Dispose() }
    }
} finally {
    $source.Dispose()
}

这个拆分脚本会覆盖同名输出分卷。确认目录里没有要保留的同名文件；若之前拆分过更大的版本，重拆前还要检查旧的高编号分卷，避免重组时混入过期分卷。源文件本身不会被修改。可把 100MB 改成需要的分块大小。此方法按字节切块，文本内容可能在行中间或多字节字符中间断开。

REJOIN

按顺序重新拼回二进制文件

用 PowerShell 读取编号分卷并按文件名顺序逐段写出，适用于上面脚本生成的分卷：

$parts = Get-ChildItem -File '.\large.iso.part*' | Sort-Object Name
$destination = [IO.File]::Create('.\large-restored.iso')
try {
    foreach ($part in $parts) {
        $source = [IO.File]::OpenRead($part.FullName)
        try { $source.CopyTo($destination) }
        finally { $source.Dispose() }
    }
} finally {
    $destination.Dispose()
}

把文件名模式改成你的分卷前缀，输出文件要使用不同名称并放在不会匹配到分卷的路径。要确认拼接无误，可比较原文件和还原文件的 SHA-256 哈希值。

完整性核对

拆分、传输、重组后，若有原文件可用，对比原文件和还原文件的 SHA-256：Get-FileHash .\large.iso, .\large-restored.iso -Algorithm SHA256。两行哈希值相同，才说明两份文件内容一致。没有原文件哈希时，“命令成功”本身不能证明分卷齐全或顺序正确。

04 / FILESYSTEM

常见 Windows 系统目录

路径地图

Windows 安装位置不一定是 C:\Windows。先在文件资源管理器地址栏输入环境变量（如 %windir%）可以跳转到当前设备对应的位置。目录中的内容由系统、服务或安装程序管理。

路径 / 变量主要用途阅读时的注意点
%windir%常见为 C:\WindowsWindows 安装目录。包含系统组件、字体、日志、配置和其他系统资源。不要通过手动删除文件来“清理”此目录。
%windir%\System32系统工具、服务程序和系统组件所在目录。在 64 位 Windows 上，这里通常放 64 位系统文件；目录名沿用历史命名。
%windir%\SysWOW6464 位 Windows 用于兼容运行 32 位程序的系统组件目录。名字容易误读：这里通常是 32 位组件，不是“另一套 64 位系统”。
%windir%\WinSxSWindows 组件存储，供系统维护、启用可选功能及更新等操作使用。资源管理器显示的大小可能包含硬链接重复计算；不要手动删除或搬动。
%windir%\System32\DriverStore\FileRepository驱动程序包的存储位置，供 Windows 安装或维护设备驱动。卸载驱动或清理驱动包应使用系统工具，避免直接删目录。
%ProgramData%常见为 C:\ProgramData供这台电脑上的所有用户共享的应用数据。通常隐藏；具体内容由对应软件管理。
%AppData% / %LocalAppData%当前用户的应用数据：漫游配置通常在 Roaming，本机缓存等常在 Local。每个用户各有一份；删除数据可能重置应用设置或丢失本地数据。
%windir%\System32\config多个系统注册表配置单元的支持文件所在位置。这是注册表底层数据文件，不是用来直接编辑的文本配置目录。
System Volume Information卷级系统数据，可能与系统还原、索引或卷管理功能有关。受系统保护；不要强行更改权限或删除里面的内容。
用户配置文件、个人文件夹与应用数据

用户配置文件通常位于 %USERPROFILE%（常见为 C:\Users\用户名），其中既有用户可见文件夹，也有隐藏的应用配置目录。企业策略、OneDrive 已知文件夹重定向和系统升级可能改变实际路径；要查看机器上的准确位置，优先使用环境变量、文件资源管理器属性或系统 API。

路径 / 变量用途排查提示
%USERPROFILE%当前用户配置文件根目录，常见为 C:\Users\用户名。用户配置文件可能包含隐藏项目；不同账号相互独立。
%USERPROFILE%\Desktop、Documents、Downloads、Pictures、Videos常见的个人文件夹。可被移动或重定向；不能仅凭默认路径断定数据位置。
%AppData%通常为 %USERPROFILE%\AppData\Roaming当前用户的漫游应用数据，常存放小型设置、配置文件等。“Roaming”是用途惯例；是否同步由配置文件类型和环境决定，并不意味着每台电脑都在实时同步。
%LocalAppData%通常为 %USERPROFILE%\AppData\Local当前用户本机应用数据，常见缓存、较大的本地数据或设备相关设置。清理前要区分缓存与用户数据；目录名不保证内容可安全删除。
%USERPROFILE%\AppData\LocalLow部分低完整性级别或受限应用使用的用户数据位置。具体用途由应用决定。
%PUBLIC%这台电脑上各用户可共享的公共配置文件，常见为 C:\Users\Public。桌面、文档等公共项目可能位于其子目录。
%ProgramData%整台电脑范围内供多个用户或服务使用的应用数据，常见为 C:\ProgramData。通常隐藏；程序可能把许可、更新或共享配置放在不同子目录。

环境变量可在文件资源管理器地址栏中直接输入，也可在 PowerShell 查看：Get-ChildItem Env:USERPROFILE, Env:APPDATA, Env:LOCALAPPDATA, Env:PROGRAMDATA。这些变量依赖当前进程/用户环境，别将某台电脑上的固定路径直接套用到其他设备。

系统组件、驱动与程序安装目录
路径主要用途阅读提示
%ProgramFiles%常见的 64 位桌面程序安装目录，通常为 C:\Program Files。安装程序可以选择其他磁盘或自定义路径。
%ProgramFiles(x86)%64 位 Windows 上常见的 32 位程序安装目录，通常为 C:\Program Files (x86)。32 位程序也可能安装在其他位置；目录名不等于程序兼容性判断。
%CommonProgramFiles% / %CommonProgramFiles(x86)%各程序共享的支持组件目录，通常位于对应 Program Files 下的 Common Files。应用安装或卸载可能会维护这些文件。
%windir%\System32\drivers系统和设备驱动相关文件的常见位置。驱动包管理应通过设备管理器、PnPUtil 或厂商安装程序完成，不要手工覆盖文件。
%windir%\System32\DriverStore\FileRepositoryWindows 驱动程序包存储区，用于安装和维护驱动。不是普通“旧驱动备份文件夹”；使用系统提供的驱动管理手段维护。
%windir%\InstallerWindows Installer 管理的安装缓存之一。与已安装程序的维护、修复或卸载有关；不要通过手动删文件释放空间。
%windir%\System32\config系统注册表 hive 支持文件常见位置。其中是系统管理的数据文件，不是文本配置文件；应通过注册表工具/API 访问注册表。
日志、更新缓存、临时文件与恢复数据
路径常见内容排查提示
%windir%\Logs\CBS组件服务与 Windows servicing 操作的日志，常见文件包括 CBS.log。排查系统文件修复、更新和组件维护问题时可参考；日志可能轮换或压缩。
%windir%\Logs\DISMDISM 相关维护操作的日志，常见为 dism.log。按时间和操作内容关联 CBS 日志，日志保留情况取决于系统维护。
%windir%\PantherWindows 安装、升级或部署阶段的部分日志和状态文件。文件可能包含设备或用户环境信息；分享前检查敏感内容。
%windir%\INF设备安装信息文件（INF）以及设备驱动安装日志等。setupapi.dev.log 可协助检查设备安装；它不是完整的设备使用历史。
%windir%\SoftwareDistributionWindows Update 工作数据和下载缓存等。遇到更新故障时使用官方疑难解答或维护流程；不要在更新进行中直接删除内容。
%TEMP% / %TMP%当前用户进程使用的临时文件位置，常在用户配置文件内。路径可按用户或策略变化；被使用的文件可能无法删除。
%windir%\Temp系统范围的临时文件位置之一。需要管理员权限的服务可能使用此目录；清理时使用存储设置或磁盘清理等受支持方式。
%SystemDrive%\$Recycle.Bin各卷回收站数据的系统管理位置。内容按用户和卷组织，直接查看可能需要权限；回收站界面是常规管理入口。
Recovery / EFI 系统分区恢复环境或启动所需的分区/文件位置；EFI 系统分区常无盘符。不是普通资料目录。不要格式化、改盘符或移动文件，除非正在按可靠的恢复/部署流程操作。

日志是特定组件在特定时间记录的信息，不等于系统的完整审计历史。记录是否存在、覆盖策略和系统版本都会影响可见范围。

为什么 32 位程序看到的路径会不同？

在 64 位 Windows 上，WOW64 会为部分 32 位程序提供文件系统重定向和注册表视图。例如，32 位程序访问 System32 时可能被重定向到 SysWOW64。因此，排查路径时要同时确认程序本身是 32 位还是 64 位。

05 / REGISTRY TREE

注册表是一棵配置树

结构拆解

注册表是 Windows 内核组件、服务、驱动、桌面应用和用户配置共同使用的分层数据库，可保存系统及应用配置、设备与服务参数、文件类型关联、COM 注册和策略等信息。它不是单一文本文件：每个节点（键）可以继续包含子键和值。许多应用也会把配置保存在 JSON/XML 文件、数据库或云端；注册表不包含完整的应用清单或操作历史，不能仅凭某个键存在就断言程序曾经运行或设备曾经被使用。

键、值、默认值、权限：看懂完整结构
键是容器

键（Key）可以继续包含子键和值。路径分隔符是反斜杠；键名在 Windows 注册表中不区分大小写。没有值的键仍然可以有意义，应用也可能只通过键是否存在来判断状态。

值由名称、类型和数据组成

一个键可包含多个值。注册表编辑器中显示为“(默认)”的项目通常是未命名值；它和键本身不是一回事。有些键没有未命名值。

权限属于键

键有安全描述符和访问控制权限；不同账户、管理员权限和系统组件能读取或修改的范围可能不同。拒绝访问不代表路径不存在，不要为方便而接管系统键权限。

数据可能有版本与上下文

同一路径在不同 Windows 版本、应用版本、用户账户、处理器架构或策略下可能不同。值名相同也不保证含义相同，先看来源和适用范围。

注册表编辑器左侧的“文件夹”是键，右侧的每一行是一个值。键的完整路径需要从根键开始；值数据的显示形式由类型决定，REG_DWORD 可在十进制或十六进制之间切换查看。

32 位与 64 位程序看到的注册表可能不同

在 64 位 Windows 上，WOW64 会为部分注册表路径提供 32 位和 64 位逻辑视图。程序通常通过系统 API 访问自己对应的视图；某些键共享，另一些会被重定向。因此，同一逻辑路径可能查询到不同数据。

  • Wow6432Node 是系统用于呈现部分重定向数据的实现细节；不建议应用直接硬编码访问这个物理位置。
  • 查询时可显式指定视图，例如 reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion" /reg:32 或 /reg:64；可用性取决于系统架构。
  • 核对软件设置时，记录应用是 32 位还是 64 位、实际查询工具和注册表视图。

HKCR 本身也是合并视图，组合了计算机范围和当前用户范围的 Classes 注册信息。遇到文件关联或 COM 注册差异时，用户范围配置可能覆盖计算机范围结果。

注册表 hive 文件在哪里，为什么不要直接编辑

Hive 是逻辑上成组的键、子键和值，Windows 会在启动或用户登录时加载并管理。机器范围的 hive 支持文件常见于 %windir%\System32\config；每个用户配置文件通常有 NTUSER.DAT，用户类注册表也可能有 UsrClass.dat。这些文件可能配有事务日志，并在系统运行时被锁定或缓存。

注册表编辑器展示的是系统管理的数据库视图，而不是这些文件的纯文本内容。不要用文本编辑器、文件清理器或手工复制/删除方式修改 hive 文件；离线维护应使用 Windows 恢复或受支持的注册表工具流程。

使用命令只读查询、导出备份

以下示例用于读取指定路径或导出所选键；导出的 .reg 只覆盖选定子树，不等于整机备份。导入 .reg 文件会修改注册表，执行前要核对目标路径、内容和恢复办法。

查询系统版本信息
reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion" /v ProductName
Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion' -Name ProductName
按名称查询服务配置（先替换服务名）
reg query "HKLM\SYSTEM\CurrentControlSet\Services\服务名"
导出准备修改的键到用户目录
reg export "HKCU\Software\Contoso" "$env:USERPROFILE\Desktop\Contoso-backup.reg"
  1. 先通过设置页、服务管理器、组策略或应用设置等受支持界面完成配置。
  2. 确需编辑时，按可信的、针对当前版本的步骤操作，只改指定值；先导出相关键并确认导出文件可读。
  3. 不要把网络上来源不明的 .reg 文件直接合并到注册表；恢复前确认导入范围，复杂故障使用系统备份/恢复方案。

提示：根键有些是系统提供的视图或别名

例如 HKCU 与 HKCC 便于程序访问特定配置；并非每个根键都对应一个可以直接在磁盘上找到的同名文件。注册表配置单元（hive）会由系统从支持文件加载并管理。

08 / READ SAFELY

读注册表时的几个原则

安全边界
01
优先使用设置页和官方工具

如果只是查看 Windows 版本或硬件，先用“设置 → 系统 → 关于”、系统信息或设备管理器。

02
记录完整路径和数据类型

只截取一个数值很容易失去上下文；同时记录根键、子键路径、值名称、类型和数据。

03
编辑前导出备份

注册表编辑器可对选中的键执行“导出”。确认备份和恢复方式后，再按可信的具体说明修改。

04
不要把注册表清理当作提速手段

不要批量删除“不认识”的键。错误的改动可能导致应用、驱动或 Windows 功能异常。

09 / REGISTRY FORENSICS

注册表历史痕迹：程序、文件、设备与网络

取证线索

Windows 注册表会保留部分用户和系统活动痕迹，但它不是完整审计日志。不同 Windows 版本、用户配置、启动方式、清理策略和系统状态都会影响记录。以下内容用于定位和交叉验证：单个键或值通常只能支持某种解释，不能单独证明某人执行、打开、复制或连接了什么。

程序执行痕迹：程序可能何时、以什么方式出现
痕迹常见位置可提供的线索解释边界
UserAssist用户的 NTUSER.DAT：Software\Microsoft\Windows\CurrentVersion\Explorer\UserAssist\{GUID}\Count部分通过 Windows Shell / Explorer 交互启动的项目；Count 项名称常经 ROT13 编码。按 Windows 版本解析后，记录可能包含运行计数、最后运行 FILETIME，以及焦点时长等字段。不是所有程序都会记录，命令行、服务、计划任务等启动方式可能不在其中。GUID 和二进制字段布局因版本而异；用版本感知的解析器，不要仅按固定偏移推断。
BAM / DAMSYSTEM\CurrentControlSet\Services\bam\State\UserSettings\{SID}、SYSTEM\CurrentControlSet\Services\dam\State\UserSettings\{SID}；部分旧版 Windows 10 路径没有 State 层BAM（Background Activity Moderator）及 DAM（Desktop Activity Moderator）相关记录可把某些可执行文件路径与用户 SID、最近活动时间关联起来。覆盖范围、路径和记录保留受 Windows 构建及策略影响；不是“每个二进制都记录”的通用进程日志。时间的写入时机可能与进程创建、结束有关。离线 SYSTEM hive 中应先解析正确的 ControlSet，再解释 FILETIME。
Amcache%SystemRoot%\AppCompat\Programs\Amcache.hve兼容性与程序清单相关数据，视版本和记录类型可能有文件路径、文件标识、发布者、元数据及 SHA-1 字段，可协助识别文件。Amcache 是清单/兼容性数据源，不是可靠的逐次执行日志；出现记录本身不能证明程序运行过。哈希字段的算法/覆盖范围依记录类型和系统版本而异；部分可执行文件条目的 SHA-1 可能只计算文件前约 31 MB，不能未经核实就当作完整文件 SHA-1。
AppCompatCache / ShimCacheSYSTEM hive：SYSTEM\CurrentControlSet\Control\Session Manager\AppCompatCache兼容性缓存可能包含路径及文件元数据（例如文件最后修改时间），可用于判断系统曾观察或处理过某个程序路径。其中的文件时间不是程序运行时间。现代 Windows 上 ShimCache 条目不能单独证明执行；不同版本的结构和含义不同，应按系统版本解析并与其他执行痕迹比对。
MUICache用户 hive 中常见：Software\Classes\Local Settings\Software\Microsoft\Windows\Shell\MuiCache；旧版本位置可能不同，也可能涉及 UsrClass.dat缓存可执行文件的显示名称、资源字符串等 Shell/MUI 信息，能帮助把路径与界面显示名称对应起来。它不是“最近运行程序列表”。字符串可能由 Shell 浏览、资源读取或其他兼容行为产生，单独存在不能证明执行。

ShellBagsNTUSER.DAT 和 UsrClass.dat 中 Shell 的 BagMRU / Bags 相关键记录资源管理器命名空间中的文件夹节点及部分视图设置；在特定条件下可保留已移动或删除文件夹的路径线索。支持“Shell 曾处理/显示该文件夹”的判断，不证明文件夹内某个具体文件被打开或复制。结构复杂且依版本变化，需用专用解析器。

MRU（最近使用）条目可能在程序卸载或清理其他历史后继续存在，但这并非保证：专门清理、策略、配置文件重建或后续覆盖都可能移除它们。记录缺失不能证明用户未进行过相关操作。

USB 设备痕迹：识别设备、卷和盘符之间的关系
痕迹常见位置可提供的线索解释边界
USBSTORSYSTEM hive：SYSTEM\CurrentControlSet\Enum\USBSTORUSB 大容量存储设备的枚举实例，可能含厂商/产品描述、设备实例 ID 和序列号样式标识。并非所有设备都有可用的唯一序列号；实例 ID 也可能依赖端口。设备实例子键的 LastWriteTime 有时可作为最近枚举/连接活动的时间线索，但不保证等于准确插入或拔出时刻；首次连接时间也不能仅凭该值确定。若出现 UMB 命名的类/实例，应按本机对应 INF、设备节点和驱动解释；它不是所有 Windows 版本通用的 USB 历史路径。
MountedDevicesSYSTEM\MountedDevices卷设备标识与盘符/挂载名的映射线索，可帮助把设备卷与其他用户文件痕迹关联。这是映射信息，不是按时间排列的完整插拔历史；盘符可能重用，必须结合卷标识、设备实例、LNK/Jump List 等核对。
Enum\USB / 其他设备类SYSTEM\CurrentControlSet\Enum\USB 等USB 设备及其接口、复合设备节点和硬件 ID 的补充信息。节点结构会因设备类别、驱动和 Windows 版本而不同；不要假设所有 USB 设备都出现在 USBSTOR。应以实际设备实例路径为准。
SetupAPI 安装日志%windir%\inf\setupapi.dev.log设备安装和驱动配置过程的时间记录，可与实例 ID、VID/PID 或设备描述交叉查找。它记录的是安装/配置活动，不是完整的插拔日志；轮换、清理或系统升级会影响可用历史。

更完整的关联通常需要把 SYSTEM 中的设备实例与 MountedDevices 的卷映射、用户 hive 中的 ShellBags/RecentDocs，以及文件系统中的 LNK 和 Jump Lists 放到同一时间线上。即使链条吻合，也要区分“设备连接”“文件被列出/选择”和“文件内容确实被复制”。

网络历史：网络配置文件、网关特征与 DHCP 租约
痕迹常见位置可提供的线索解释边界
NetworkList\ProfilesSOFTWARE hive：Microsoft\Windows NT\CurrentVersion\NetworkList\Profiles\{GUID}网络配置文件名称/描述、类别、网络类型，以及部分版本中的 DateCreated（配置文件创建时间）和 DateLastConnected（最后连接时间）。无线网络通常以 SSID 命名，有线网络也可能形成配置文件。配置文件字段不是每次连接事件的完整清单；最后连接值会被后续连接更新。SSID 可重复或伪造，单靠它不能确定设备的物理位置。
NetworkList\SignaturesSOFTWARE\Microsoft\Windows NT\CurrentVersion\NetworkList\Signatures\Managed / SOFTWARE\Microsoft\Windows NT\CurrentVersion\NetworkList\Signatures\Unmanaged可与配置文件关联的网络签名信息，例如 DNS 后缀、网关 MAC 等，帮助区分网络环境。不是全球唯一地理坐标；网关、虚拟网络、VPN 和企业网络结构都会影响解释。需与 WLAN 事件、DHCP、SRUM 或其他来源互证。
TCP/IP 接口与 DHCPSYSTEM hive：SYSTEM\CurrentControlSet\Services\Tcpip\Parameters\Interfaces\{GUID}接口配置、DHCP/静态配置、DHCP 服务器、DNS 和租约相关值；有助于了解某接口曾使用的网络参数。部分接口记录可见 LeaseObtainedTime、LeaseTerminatesTime 以及 T1/T2 续租时间；传统参数文档将租约时间记为自 1970-01-01 起的秒数。动态配置会被新租约覆盖，静态地址没有 DHCP 租期；不同版本/接口字段和表示可能不同。不能仅凭当前值重建完整网络连接时间线。

NetworkList 中 DateCreated / DateLastConnected 字段与注册表键 LastWriteTime 不是同一种时间；前者在常见实现中为本地时间结构，后者是 UTC FILETIME。使用解析器时核实字段格式、时区和 Windows 版本。网络配置文件也可能被用户“忘记网络”或系统管理操作删除。

取证陷阱：LastWriteTime、事务日志、清理与证据链
LastWriteTime 只锚定键的修改

它表示键最后一次被修改的时间，不会指出哪一个值发生变化，也不必然等于程序安装、首次运行、USB 插入或网络连接时间。父键和子键应分开记录并按具体 artifact 解释。

日志不是可依赖的“删除回收站”

Hive 旁的 .LOG1 / .LOG2 用于注册表事务与一致性恢复，可能含主 hive 尚未合并的写入；它们不是保证保留已删除键的完整历史数据库。

主 hive 与活跃系统可能不同步

系统运行期间 hive 仍可能有缓存或未合并写入。采集时应保持证据一致性，并将主 hive 与同目录事务日志一并保存、计算哈希，再由支持日志恢复的解析器处理。

缺失与稀疏记录都要谨慎

版本差异、未启用功能、用户配置未加载、记录覆盖、清理工具和攻击者删除都可能造成空缺。稀疏本身值得进一步调查，但不能单独推出“有人清理过”。

示例关联：USBSTOR 可协助识别设备实例，MountedDevices 提供卷/盘符映射，LNK 或 Jump List 可包含文件路径和时间，RecentDocs/ShellBags 则提供用户配置层面的补充线索。只有在用户、设备/卷标识和经过时区校正的时间线都能相互对应时，才适合提出较强解释；这些痕迹仍不能单独证明文件内容被复制或某个人实施了操作。
